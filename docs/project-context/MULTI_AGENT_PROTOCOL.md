# MULTI_AGENT_PROTOCOL — 複数AI協調 運用規約

**Claude / ChatGPT / Codex / Gemini が同一リポジトリで並行作業するための強制ルール。**
全AIは作業開始前に本書と `CANONICAL_SOURCES.md` を読む。人間(Yuki)が最終権限を持つ。
最終更新: 2026-07-19(ChatGPT・Geminiのインシデント2件を反映。詳細は `INCIDENTS.md`)

---

## 0. 三原則(これだけは絶対)

1. **境界を越えない** — 指示された対象(ファイル・カット・関数)だけを触る。波及変更は自分でやらず確認する。
2. **先回りしない** — 最新版の存在に気づいても、明示指示がなければ全体へ適用・同期・再生成しない。
3. **壊す前に止まる** — 上書き・削除・force push・merge・重い一括処理は、実行前に人間の許可を取る。

---

## 1. 作業スコープの厳守(Geminiインシデント対策)

- 指示された**特定のターゲットのみ**に手を加える。「C18を作って」= C18だけ。他カットの設定JSON・字幕・MOVに触れない
- 他ファイルへ波及する変更が必要になったら、**自分で実行せず**確認する:
  「〇〇も更新が必要ですが、実行してよいですか?(影響範囲: …)」
- **禁止**: 「同期のため」「本番ですぐ使えるように」等の自己正当化で、指示外のファイルを上書き・再生成すること

## 2. 先回り(お節介同期)の完全禁止

- 最新ファイル(例: コンテv2)の存在に気づいても、「それを全体へ適用して」と明示されない限り、
  設定・字幕・素材の一括同期/再ビルドを**実行しない**。それは他エージェントのタスクか、保留中の可能性がある
- 「最新に合わせるべき」と思ったら、実行ではなく**提案**する

## 3. 曖昧な指示は狭く確認してから動く

- 「とりあえず作って」「適用して」等は、範囲を勝手に決めない。
  「C18のみですか? 全体ですか?」と**ピンポイント化**してから、最小範囲で着手する
- 迷ったら広くやらず、狭くやって「ここまでやりました。続けますか?」で止める

## 4. 重い一括処理は事前申請(Geminiインシデント対策)

- 実行に**数分以上**かかる処理(全カットのProRes書き出し、大量レンダー、大規模ビルド)は、
  事前に「〇〇に約N分かかります。今実行してよいですか?」と許可を取る
- 共有マシンのCPU/GPU/ストレージを占有する処理は、他エージェントのプレビューや人間の操作を阻害する前提で扱う

## 5. 作業宣言(排他制御)

- 作業開始時に宣言する:「私(Claude)は `docs/design_reference/*` と第1回コンテを担当。ブランチ `xxx` で作業開始」
- 同一ファイルを複数AIが同時編集しない。担当領域は §7 の分担に従う

## 6. 正本確認プロトコル(ChatGPTインシデント対策)

カット番号・コンテ・台本について問われたら、次の順で確認する:
1. `CANONICAL_SOURCES.md` で対象回の**最新正本**を確認
2. 正本ファイル名を**完全一致**で特定(v1/v2の取り違え防止)
3. mainに無ければ `git fetch --all` → 全リモートブランチ → open PR を確認
4. 対象ファイルを**実際に取得して中身を読む**(名前だけで判断しない)
5. カット番号・ナレ・映像内容・尺・MG IDを照合
6. 旧版しか見られていないなら「これは旧版(v1)です」と**明示**
7. 全確認前に「存在しない」と**断定しない**(§CANONICAL 4の限定表現を使う)

## 7. 担当境界(書き込み領域の分割)★衝突を最も減らす

| AI | 主担当(書き込んでよい領域) | 触らない |
|---|---|---|
| **Claude** | 設計・仕様(`docs/`)・台本・コンテ(`conte/`)・生成スクリプト(`tools/`)・ブレーン(方針/構成/レビュー) | Remotion実装コード・重いレンダー |
| **Codex** | Remotion実装(`remotion_mg/src`・`data`)・検証ゲート実行・レンダー(申請の上) | 台本・コンテの内容改変(指示なしに) |
| **Gemini** | 静止画生成(人物・背景・テクスチャ → `remotion_mg/public/`配下の素材)・画像加工 | 設定JSON/字幕/コンテの一括上書き・レンダー |
| **ChatGPT** | 調査・レビュー・文書校正・出典確認 | 破壊的なファイル操作全般 |

- 領域をまたぐ必要が出たら、担当AIに渡すか、人間に確認する(自分でやらない)
- 人間(Yuki)は全領域の最終決定者。ゲート承認・破壊的操作の許可を出す

## 8. ブランチ / コミット / PR 規約

- **ブランチ命名**: `docs/*`(設計) / `feature/*`(機能) / `agent/<ai>-<topic>`(AI個別作業) / `chore/*`(整理)
- **他AIの未コミット作業を巻き込まない**: `git add` は自分の担当ファイルを明示指定(`git add -A` 禁止)。
  ステージ前に `git status` で他者の変更が混ざっていないか確認
- **index.lock**: 残っていたら `rm -f .git/index.lock`(他のgitプロセスが動いていないことを確認してから)
- **1 PR = 1 目的**: コンテv2・Remotim実装・素材追加・LineCompare修正は**別PR**に分ける。
  分割困難なら、PRタイトルと本文を**実際の変更範囲に一致**させる(タイトル詐称禁止=PR #5の反省)
- **PR本文に正本変更を明記**: 旧正本 / 新正本 / 適用コミット / 旧版の扱い / 参照ブランチ / 今後参照すべきファイル

## 9. 破壊的操作は人間承認(例外なし)

以下は**人間の明示承認なしに実行しない**:
- ファイル/ブランチの削除・移動・リネーム
- 既存ファイルの上書き(自分の担当外)
- force push / rebase の共有ブランチへの適用
- PRのmerge
- 重い一括レンダー/ビルド(§4)

破壊的整理をする場合も、**削除前に差分を確認**し、Remotionコード・素材を失わないことを保証してから、承認を得る。

## 10. インシデントはルールに変換する

事故が起きたら叱責でなく**ルール化**して `INCIDENTS.md` に追記し、本書に反映する。
「誰が悪いか」でなく「どの規約があれば防げたか」で運用を育てる。
